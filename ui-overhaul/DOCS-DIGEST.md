# Docs digest: docs/user/*.md

Source: `docs/user/*.md` (39 files). Purpose: a reference so audit agents do not propose
features that already exist. Tags: `[web]`, `[desktop]`, `[mobile]`, `[all]` follow the doc's own
wording; a bullet with no platform named in the doc is tagged `[all]`. `[cli]` marks server or
command-line behaviour (outside the three clients). Paths written as `**Settings → ...**` are verbatim;
where a doc writes `Settings > ...` it is quoted as written and flagged.

## activity-log.md

- [web] [desktop] Consecutive tool calls collapse into one expandable summary; opening it shows commands, tool inputs, status and exit codes.
- [web] [desktop] Expanding a single tool call shows its output. A running command's output updates live; long output shows only its most recent part.
- [web] [desktop] **Open diff** on a file change opens its contents for review.
- [web] [desktop] T3 Orchestrator summaries describe actions taken (for example "Ran 2 commands and sent messages to 3 threads"); repeated messages to the same destination show both counts.
- Thread creation counts the threads returned by the tool, including batches.
- Groups with many kinds of activity show up to two specific action categories plus a count of the rest. Commands, file changes and orchestration changes take priority over reads and status checks. Expanding the group shows the full list.
- Failed calls do not count as successful messages or creations.
- Waiting on a thread does not mean it finished; an interrupt or cancellation request does not mean the thread stopped.
- When tool details are unavailable, summaries use a broader description rather than guessing counts.

Settings paths: none.
Shortcuts: none.
States and messages: "Ran 2 commands and sent messages to 3 threads"; "Sent 5 messages to 2 threads"; **Open diff**.

## appearance.md

- [web] [desktop] **Settings → Appearance** chooses a theme and follows the system appearance or stays in light or dark mode. Separate themes for light and dark are picked by selecting the preview within each theme. Appearance preferences are saved per device or browser.
- [web] [desktop] Command palette **Change theme** selects a theme without leaving chat.
- [web] [desktop] Command palette **Change appearance** picks System, Light or Dark independently of the theme.
- [web] [desktop] Shortcuts open the theme picker and cycle the appearance mode (see Shortcuts). Both are customisable under **Settings → Keybindings**.
- [mobile] **Settings → Appearance** has its own themes and text, code and terminal preferences. Mobile does not follow environment themes or defaults.
- [mobile] Android 12+: the **Material You** theme uses wallpaper colours; selecting another theme replaces them. It can be chosen separately for light and dark. **Material You Layout** is on by default unless turned off in Appearance and changes shapes, spacing and controls independently of the theme.
- [web] [desktop] **Composer context** (toggle in Appearance): keeps branch and worktree controls visible below the composer after the thread starts. Git-backed projects show these controls while creating a thread; they retreat when the composer docks after the first message. Applies to web and desktop only.
- [all] **Render math** (in **Settings → Appearance**) typesets LaTeX in messages and Markdown previews: `$…$`, `$$…$$`, `\(…\)`, `\[…\]` and fenced `math` blocks. Dollar amounts stay text; `\$` keeps a literal dollar sign. Wide formulas scroll horizontally. Copying or exporting preserves TeX. The composer keeps TeX source editable. Saved per device.
- [web] [desktop] **Panel animations** slider: main sidebar, right panel and terminal drawer open and close immediately by default; moving the slider above 0 ms adds motion up to 400 ms unless the OS reduced-motion setting is on. Switching threads snaps to the selected thread's panel state.
- [web] [desktop] **Create theme** adjusts a palette or imports a T3 Code or VS Code theme. The theme editor's colour picker selects an area of the app to find the colour to change. Themes export as JSON.
- Environment themes (server-published): a published theme selected in **Settings → Appearance** follows the palette as the server updates it. **Duplicate** makes an editable independent copy. A saved custom theme with the same ID takes precedence. If the server stops publishing the selected theme, T3 Code falls back to its standard theme. app.t3.codes and additional connections do not use environment themes.
- [cli] Server defaults: `t3 theme set <name>`, `t3 theme clear` (removes default without changing current themes), `t3 theme show` (lists default and published themes). Offline clients apply the default when they reconnect; each client applies it once.
- [cli] Publishing a theme: JSON saved in `~/.t3/userdata/themes/` (filename is the theme ID; `system`, `light`, `dark` and built-in IDs are reserved). A short format takes `name`, `appearance` (light or dark), `canvas`, `accent` and optional `colors` overrides; T3 Code generates the rest.

Settings paths: **Settings → Appearance**; **Settings → Keybindings**.
Shortcuts:

- Cmd+Option+A (macOS) / Ctrl+Alt+A (Windows/Linux): opens the theme picker directly.
- Cmd+Option+Shift+A (macOS) / Ctrl+Alt+Shift+A (Windows/Linux): cycles System, Light and Dark.
  States and messages: "Change theme"; "Change appearance"; "Create theme"; "Duplicate"; "Material You"; "Material You Layout"; "Composer context"; "Render math"; "Panel animations"; System / Light / Dark.

## background-service.md

- [cli] Linux and macOS only: T3 Code runs as a per-user service so no terminal needs to stay open. Windows background services are not supported.
- [cli] `t3 service install` (install and start); `t3 service status` (status and log path); `t3 service restart`; `t3 service uninstall` (stop and remove from startup, keeps projects, threads and settings).
- [cli] `t3 update` switches `t3` and the service to the newest release on your channel. Restarting interrupts agent turns, terminals and remote clients, so it asks first (`--yes` skips). Pin with `t3 update 0.0.42`, switch trains with `--channel nightly`, move backwards with `--allow-downgrade`. `preview` builds are never offered as updates.
- [cli] `t3 uninstall` removes the service, the `t3` launcher and downloaded versions after listing them and asking once; `~/.t3/userdata` and `service.env` are kept.
- [cli] Local network access: the service listens on local-network and Tailscale addresses so desktop and mobile apps connect directly without T3 Connect. app.t3.codes stays on T3 Connect. `T3CODE_HOST=127.0.0.1` in `service.env` limits it to this machine.
- [cli] `service.env` (normally `~/.t3/service.env`) holds custom environment variables; restart after editing; `chmod 600` when it holds credentials.
- [cli] Linux needs systemd user services and enables lingering so the service survives logout and boot. macOS starts the service at login and stops it at logout.
- [cli] T3 Connect can offer service installation during setup; signing out of T3 Connect does not stop or uninstall the service.
- [cli] `t3 doctor` reports database size and reclaimable space and offers repairs; `--fix` runs recommended repairs, `--dry-run` only reports, `--base-dir` picks another data directory. Superseded internal history is removed automatically while the server runs.
- [web] [desktop] Reclaim-space suggestion appears in **Settings > Storage** when at least 1 GiB can be reclaimed (doc writes `>`, not `→`).
- [mobile] Reclaim-space suggestion appears in **Settings > Maintenance** (doc writes `>`).

Settings paths: **Settings > Storage** (web and desktop, written with `>` in the doc); **Settings > Maintenance** (mobile, written with `>`); **System Settings → General → Login Items** (macOS, OS path, not a T3 setting).
Shortcuts: none.
States and messages: service status codes `linger-unavailable`, `user-manager-unavailable`, `service-disabled`, `service-stopped`, `restart-pending`, `linger-disabled` (from `t3 service status`); "Run `t3 service restart`" .

## browser-import.md

- [desktop] **Settings → Integrations → Browser profiles → Add profile**, then choose a browser under **Import from** to copy cookies from another browser into the preview browser.
- [desktop] One-time copy: later login changes stay separate between the two browsers; some sites may still ask for sign-in.
- [desktop] Close the source browser before importing; allow an OS keyring unlock prompt if one appears.

- [desktop] Windows: Firefox and Helium profiles with standard encryption are supported; Chromium-based browsers with app-bound encryption cannot be imported. Partitioned cookies are skipped on all platforms.

Settings paths: **Settings → Integrations → Browser profiles → Add profile**.
Shortcuts: none.
States and messages: **Add profile**; **Import from**; **Allow**; **Continue**.

## composer.md

- [all] Messages hold up to 120,000 characters; longer drafts stay in the composer. A paste of 32 KiB or more (or one that would exceed the limit) becomes a text-file attachment; Cmd+Shift+V (Apple) / Ctrl+Shift+V keeps a large paste editable on a hardware keyboard.
- [all] Markdown is styled as you type; markers such as `**` stay visible when the cursor is on them. Line starts `- `, `1. `, `- [ ] `, `> `, `# `, `---` become lists, task lists, quotes, headings and rules; a line with three backticks plus Enter opens a code block; `#1234` looks up a pull request. The agent receives the text as typed.
- [all] Enter sends. Shift+Enter continues a list or quote (empty line leaves it); Tab nests list items. In code blocks Enter keeps indentation, Tab / Shift+Tab indent the selection, a closing fence plus Enter or two blank lines at the end leave the block, Backspace at the start turns it into plain lines. Language chooser sits in the block's corner. Very large blocks skip highlighting.
- [all] Up to 100 files per message. Images up to 10 MiB each, 80 MiB of images per message. Other files (including videos) up to 50 MiB each, subject to environment limits. A video gives the agent a file path, not native video input. Uploads start when added and must finish before sending; failed uploads can be retried or removed.
- [web] [desktop] Drag or paste images; HEIC/HEIF converted to JPEG; over-limit photos resized. Reloading mid-upload means re-attaching. [mobile] HEIC/HEIF converted from the photo library; files can be sent to T3 Code from another app's system share sheet.
- [web] [desktop] **Settings → General → Follow-up behavior** chooses Queue (later turn) or Steer (interrupt the running turn) for this client. [mobile] **Settings → Follow-ups** holds the same choice; the send button shows the action while a turn runs; long-press uses the other action once.
- [mobile] Offline: drafts keep local copies of attachments, queued messages survive restarts and uploads resume on reconnect. Signing out of T3 Connect keeps this work on the device until the same account signs back in.
- [web] [desktop] **Settings → Providers → Models** adds an unlisted model with a custom name and options; only options the provider integration supports affect turns. Antigravity uses its account catalogue and does not support custom models. Built-in models can be renamed on every client through `customModels` in the server's `settings.json`.
- [all] Provider, model and options are remembered for new threads. A project's configured model takes precedence; resetting the project setting returns to the remembered selection. Unset reasoning level or service tier uses the provider's configuration.
- [web] [desktop] **Cite in composer** on a text selection inside one assistant response creates a quote chip; the pencil adds or edits a comment. Selecting the chip returns to the source. Mobile displays saved quotes but does not create them.
- [all] Recall: ArrowUp in an empty composer restores the last prompt sent in the thread (text only); ArrowUp / ArrowDown walk back and forward; editing a recalled prompt turns it into a normal draft.
- [web] [desktop] **Edit from here** rewinds to before a sent message. **Revert and keep changes** rewinds the conversation only; **Revert files too** also restores the workspace checkpoint (worktree threads only; refused when another thread or agent uses that directory). Needs provider rewind support.
- [web] [desktop] Prompt stash: Cmd+S / Ctrl+S saves the prompt and attachments; with an empty composer it restores one stash or opens the stash menu. Uploaded files in a stash are kept 24 hours; after that use **Attach again**.
- [mobile] iPhone voice input (iOS 26+): on-device transcription inserted at the selection; recordings up to five minutes. **Settings → Microphone** ranks input devices (built-in, wired, Bluetooth, CarPlay; CarPlay defaults after the built-in microphone).
- [web] [desktop] While the agent works with an empty draft the composer shows **Interrupt**. With text or attachments the send button shows a queue icon (Queue) or a steer arrow (Steer); holding Cmd / Ctrl switches to the opposite action.
- [all] Queued rows sit above the composer with thumbnails: drag the handle to reorder, promote to steer, pencil to edit (**Cancel** leaves the row unchanged; the checkmark saves), or remove. **Resume** (web/desktop) or **Resume queue** (mobile) continues a held queue after a stop or server restart.
- [all] `/` opens commands and `$` adds a skill from the selected environment and provider. Mobile offers both before a thread on **New task**. **Settings → General → Show skills in slash menu** hides skills from the slash menu. **Restart agent session** (command palette, web/desktop) applies skill, plugin or MCP changes.
- [all] `/compact` reduces context where supported (web/desktop also offer it from the context meter); Claude can compact idle threads automatically. `/goal <definition of done>` (Codex and Claude) keeps working across turns; the thread shows **Goal** and a row above the composer shows progress. `/goal` shows the goal, `/goal clear` removes it; Codex also has `/goal pause` and `/goal resume`.
- [web] [desktop] Context chips sit at the cursor: terminal excerpt, review comment, preview annotation, file, pull request (`#` search) and thread (`@` search or drag from the sidebar). Thread chips carry a reference only; the agent reads history on demand. A pull request chip is coloured by state (open, draft, merged, closed) and offers **Open pull request**. Chips survive copy and paste between drafts; stale chips show a dashed outline.
- [all] Attached files and media: web/desktop files open beside the conversation with a view toggle, **Copy contents** and **Save file**; right-click media to save or copy path or URL. Mobile file screen menu holds **Copy contents**, **Save or share** and **Open in file viewer**; touch and hold a thumbnail for **Save or share**. HTML and PDF files render; HTML can switch to source view; HTML previews cannot access the T3 Code session. Files outside the workspace open read-only.

Settings paths: **Settings → General → Follow-up behavior**; **Settings → Follow-ups** (mobile); **Settings → Providers → Models**; **Settings → Microphone** (mobile); **Settings → General → Show skills in slash menu**; **Settings → Keybindings** (shortcut customisation).
Shortcuts:

- Enter: send. Shift+Enter: continue list or quote. Tab / Shift+Tab: nest list item or indent / outdent code lines. Backspace at start of a code block: plain lines.
- Cmd+Shift+V / Ctrl+Shift+V: keep a large paste editable.
- Cmd+Enter / Ctrl+Enter: the opposite follow-up action (steer when the default is Queue, queue when the default is Steer). Add Shift for the opposite action.
- Cmd+Shift+Enter / Ctrl+Shift+Enter: send the oldest queued message as a steer. Command name `thread.steerQueuedMessage`.
- Option+Up / Alt+Up (cursor at start of composer): edit the most recently queued message. Command name `thread.editQueuedMessage`.
- ArrowUp / ArrowDown: prompt recall (empty composer, or an unedited recalled prompt).
- Cmd+S / Ctrl+S: prompt stash, or restore a stash when the composer is empty.
- Hold Cmd / Ctrl while sending: the opposite follow-up action.
  States and messages: "Interrupt"; "Resume"; "Resume queue"; "Cite in composer"; "Edit from here"; "Revert and keep changes"; "Revert files too"; "Attach again"; "Goal"; "Open pull request"; "Copy contents"; "Save file"; "Save or share"; "Open in file viewer"; "Restart agent session"; "Cancel" (queued row); "New task"; "Follow-ups"; "Queue" / "Steer"; "Terminal excerpt, Terminal 1 lines 3-4" (screen-reader chip label); dashed outline (unavailable chip).

## cursor.md

- [all] Cursor V2 runs through the official `@cursor/sdk` TypeScript package, not Cursor's ACP transport. Requires Node.js 22.13+, a paid Cursor plan, and a model the SDK accepts (`auto` is sent as the SDK `default` selection).
- [all] Sign in with **Sign in**, complete the browser sign-in, and T3 Code updates when it finishes (works on remote environments). On mobile, an already configured Cursor instance is managed under **Settings > Provider accounts**.
- [all] A `CURSOR_API_KEY` environment variable overrides browser sign-in; remove it to use the browser flow. Each provider instance keeps its own login on the environment that runs it; Cursor editor and CLI logins are separate.
- [all] **Change account** and **Sign out** stop that instance's running threads and keep their history; sign-out forgets the saved credential (revoke the key in the Cursor dashboard).
- [all] Supported: creating and resuming local Cursor agent threads; changing model and parameters between turns; streamed text, reasoning, tool activity, plans and todos; thread-scoped T3 Code MCP tools; image attachments; interrupt, queued app messages and interrupt-and-restart steering; provider conversation snapshots.
- [all] Cursor `task` subagents appear as read-only child app threads with their tool activity and final result; send messages from the parent thread.
- [all] Not exposed by the SDK: native agent fork, conversation rollback, active steering, interactive approval callbacks. Same-provider forks use the portable full-thread handoff (see portable-handoffs.md).
- [all] Runs use the local-agent runtime in the selected workspace; Cursor cloud agents are not exposed.
- [all] Runtime modes: full access disables the SDK sandbox; restricted modes normally enable it. On Windows, Auto and Supervised run without filesystem isolation when Cursor Auto-review is enabled; restricted modes without Auto-review (including the default Auto-accept edits mode) cannot start on Windows.
- [cli] Cursor binary path and API endpoint settings belong to the CLI/ACP integration; V2 execution does not launch that binary and the SDK has no endpoint override.
- [cli] Developer replay: `pnpm --filter t3 record:cursor-replay --scenario simple` records a fixture against the real SDK; `--out <path>` writes a probe without replacing a checked-in fixture.

Settings paths: **Settings > Providers > Cursor** (written with `>`); **Settings > Provider accounts** (mobile, written with `>`).
Shortcuts: none.
States and messages: **Sign in**; **Change account**; **Sign out**; "Auto-accept edits" (mode name); "Auto-review"; "Auto"; "Supervised"; "full access"; `AgentNotFoundError` (provider error named in doc).

## devices.md

- [web] [desktop] Device panel shows a live iOS Simulator or Android Emulator beside a thread (right panel → **Device** in a project thread). Agents use the same device through `device_*` tools and the `agent-device` CLI.
- [web] [desktop] First-use setup walks through three steps: starting the device hub, checking iOS and Android support, and choosing whether agents may control devices. Opening the panel alone downloads and starts nothing.
- [web] [desktop] Choose a running device to watch it, or **Start** a stopped one. Each device has its own tab (**+ → Device** adds one; double-click a tab name or **Rename** renames it). Only the visible tab streams video.
- [web] [desktop] **Float device over chat** keeps a small window over the chat; drag by its handle, resize from any edge, **Open in right panel** brings it back.
- [web] [desktop] Interaction: click and drag to touch, type when focused; toolbar Home, Back and Recents (Android), rotate (iOS), power off. Closing a tab stops watching; closed tabs stay closed after reload.
- [web] [desktop] **3D view** shows supported devices while the live screen stays interactive. iPhone Duo fold and stance controls and hinge pinch; **Restore 3D view** resets. Supported Android foldables: **Fold device** and **Unfold device**.
- [web] [desktop] **Tools** drawer: foreground app, light/dark mode, text size, accessibility settings, element-frame overlay, fake location, app permissions. iOS adds Liquid Glass, colour filters, VoiceOver and a test push; Android adds orientation and network toggling. Shows only what the platform supports.
- [web] [desktop] When an agent opens a device it floats over the chat, like an agent-driven browser; **Auto-show floating preview** (**Settings → Integrations → Browser**) switches that to a right-panel tab. Device activity also appears in the thread timeline.
- [mobile] Open the agent's thread and tap the device button above the composer to watch and control the live screen.
- [web] [desktop] **Agent device access** (**Settings → Integrations → Devices**) controls whether agents get device tools; off hides them from agents started afterwards. Restart an existing agent session after granting access.
- [web] [desktop] Simulators run on the machine that hosts the environment server. iOS needs macOS with Xcode. Android needs SDK Platform-Tools, Android Emulator and Command-line Tools (latest) plus a virtual device; `ANDROID_HOME` for custom SDK locations; restart the environment server after installing SDK tools.
- [all] Android emulator video needs `ffmpeg` with libx264 on the host PATH, or an executable named by `SERVE_EMU_FFMPEG`. Physical Android devices (scrcpy) and iOS do not need ffmpeg.
- [all] Remote: the stream goes through the environment server over local network, Tailscale and T3 Connect. Live video needs HTTPS or localhost; on plain-HTTP remote origins iOS falls back to still images and Android cannot show video.
- [web] [desktop] **Device hosts** (**Settings → Integrations → Devices**): add SSH hosts (alias or `user@host`, optional identity file and port) per environment; **Test connection** checks SSH, Node, npm and platform tools. Password prompts are not supported.
- [web] [desktop] Device tool versions install automatically when used; **Check device tool versions** (Settings → Integrations → Check device tool versions) reads versions without installing. Use **Retry** after a failed install.
- [web] [desktop] Turning off the device hub in **Settings → Integrations → Devices** stops helper processes; simulators keep running.

Settings paths: **Settings → Integrations → Devices**; **Settings → Integrations → Browser**; **Settings → Integrations → Check device tool versions** (doc phrasing; the last segment is a button).
Shortcuts: none.
States and messages: **Device**; **Start**; **+ → Device**; **Rename**; **Float device over chat**; **Open in right panel**; **3D view**; **Restore 3D view**; **Fold device**; **Unfold device**; **Tools**; **Agent device access**; **Auto-show floating preview**; **Device hosts**; **Test connection**; **Retry**; **Check device tool versions**. Env vars: `ANDROID_HOME`, `SERVE_EMU_FFMPEG`.

## guest-links.md

- [web] [desktop] [mobile] A guest link lets a teammate follow one thread in a browser and ask the agent questions with no account. Guests see messages and replies as they stream; each guest message waits until you send or dismiss it.
- [all] Beta: turn on **Settings → Beta → Guest links** on the machine running the thread. The machine must be linked through T3 Connect and stay online; turning the setting off breaks every guest link on that machine until it is turned back on (unexpired links then work again).
- [web] [desktop] Right-click a thread in the sidebar and choose **Share with guest** (also in the thread menu and the command palette).
- [all] A link works in one browser and expires after 24 hours; reopening it in that browser returns to the thread. One link per person.
- [all] Guest messages appear at the end of the thread; the sidebar shows **Request**. **Send** runs the message as a normal turn; **Dismiss** discards it. Attached files show with the message and **Send** includes them.
- [all] **Stop sharing** ends the link at once. Archiving the thread, creating a new link or unlinking the machine from T3 Connect also ends it.
- [mobile] The mobile app can send or dismiss guest messages.
- [all] Guests see the recent history and everything after, with messages, files, replies, reasoning, plans, questions and work (command output on expand). Their composer shows the model but cannot change it. They do not see diffs and cannot fork, revert, open files on the machine, or answer the agent for you.
- [all] Guest attachments: paperclip, paste or drop. Up to 4 files and 10 MB per message; images must be PNG, JPEG, GIF or WebP; waiting messages can total 20 MB.
- [all] Dismissing a message, ending the link or archiving the thread deletes the files of waiting messages; sent messages keep their files.
- [all] A guest's text and files run under the thread's current permission mode once sent.

Settings paths: **Settings → Beta → Guest links**.
Shortcuts: none.
States and messages: **Share with guest**; **Stop sharing**; **Request**; **Send**; **Dismiss**.

## html-renders.md

- [all] Agents can answer with a self-contained HTML page (chart, table, diagram, image collage or mockup) that appears above the written reply. Works with every provider on web, desktop and mobile.
- [all] Pages use the current theme, including custom themes, and follow light and dark mode. Scripts run in a sandbox separated from T3 Code and the session; links open in the browser.
- [web] [desktop] Expand button opens a page full screen; zoom controls adjust detail.
- [all] Local images referenced by file path are embedded when the page is published, so it survives moving or deleting the originals. Deleting the thread deletes its pages.
- [all] Before publishing, agents check pages with screenshots from a headless browser that T3 Code keeps for itself (never a browser you installed). The first preview on a machine downloads it once (about 120 MB) into T3 Code's data folder. Some Linux hosts need browser host setup (remote-access.md#browser-host-setup); pages publish without it.
- [all] MCP apps: an MCP server can return an interactive app (MCP Apps standard) that appears in the thread in place of the tool call on web, desktop and mobile. Codex supports this today; other providers show ordinary tool calls.
- [all] Apps follow your theme. An app asks before calling tools on its own server or posting a message (unless the tool is marked read-only); it asks before every message. On mobile an app also asks before opening a link, and T3 Code asks before saving a file an app offers.
- [all] An app stays viewable after its agent stops, but using it needs the thread's agent running; send a message first if the app says it is unavailable. An app that navigates away from its own page is stopped.
- [web] [desktop] Full screen: a tap in the app within five seconds of a click or key press elsewhere does not count. Return with the button in the app's top corner or Escape outside the app. Approvals also return the app to the thread.
- [mobile] Full screen opens the app again in its own screen, so unsaved state starts over. The app can send the latest note about what you did (such as a filter) with your next message.

Settings paths: none.
Shortcuts: Escape (outside the app, returns a full-screen app to the thread).
States and messages: "unavailable" (app state when its agent is not running; quoted as the app's message); "Codex supports this today".

## install.md

- [all] Requirements: an installed, authenticated provider before starting a thread; T3 Code can be launched and providers configured afterwards.
- [cli] Install: `curl -fsSL https://t3.codes/install.sh | sh` (macOS/Linux); `irm https://t3.codes/install.ps1 | iex` (Windows PowerShell). Installs `t3` to `~/.local/bin`. `T3CODE_CHANNEL=nightly` picks nightly; `T3CODE_VERSION` pins a version.
- [cli] Commands: `t3` (start server and open web app), `t3 serve` (no browser), `t3 service install`, `t3 update`, `t3 doctor`, `t3 uninstall`, `t3 help`. `t3 ./my-project` starts in a new directory; `npx t3@latest` tries it once.
- [cli] If a server is already running, `t3` connects to it; stop it first or use another `--base-dir`.
- [cli] Intel Macs have no `t3` executable; build from source with `vp` and run `node apps/server/dist/bin.mjs`; `t3 update` and the service do not apply.
- [desktop] Desktop packages: GitHub Releases, `winget install T3Tools.T3Code` (Windows), `brew install --cask t3-code` (macOS), `.deb` for Debian/Ubuntu (asks for a password per update), Arch `t3code-bin` and nightly `t3code-nightly-bin`.
- [desktop] **Settings → General → About** → **Install** next to **t3 command** adds the CLI to PATH; **Remove** undoes it.
- [desktop] Windows: **Settings → Connections** chooses a WSL distro for agents and projects; provider CLIs are installed inside the distro.
- [cli] `t3 app` (with the desktop app running) opens a new thread for the current directory; `t3 app ../my-project` opens another path.
- [mobile] App Store and Google Play; the phone links to a server through remote access or a pairing URL. Store links and QR codes are also under **Settings → General → Mobile app** on web and desktop. TestFlight is invite-only; Android beta APKs come from GitHub.
- [mobile] **Settings → Diagnostics** on the next successful launch lists startup crashes from the last 7 days with error and component stack; read it before sharing.
- [web] [desktop] **Settings → Providers** enables a provider per environment; provider accounts and configuration belong to that environment's machine. Add a provider instance for a separate account; environment variables such as API keys or base URL; sensitive values are hidden after saving.
- [web] [desktop] Provider CLIs must be on the server's `PATH`; otherwise set **Binary path** in provider settings. T3 Code warns on known-incompatible provider versions; the recommended version or range is shown in **Settings → Providers**. **Update now** on a provider card runs the owning installer.

## keybindings.md

- [web] [desktop] **Settings → Keybindings** customises shortcuts; the page lists the command IDs and defaults for your version.

- [web] [desktop] Pickers: `mod+shift+m` model, `mod+shift+h` host, `mod+shift+e` effort, `mod+shift+a` access mode, `mod+shift+x` workspace (current checkout, new worktree, previous worktree when available), `mod+shift+g` Git branch, `mod+shift+l` reuses the previous worktree directly. **Composer: Cycle Host** steps a new thread to the next machine (no default).

- [web] [desktop] Find: `mod+f` in a diff (Diff panel or PR Code tab) searches every file including folded files and hidden lines (not configurable); `chat.find` searches messages and proposed plans in the thread (`mod+f` outside terminals and previews; Retry on failure). - [all] Rules live in `~/.t3/userdata/keybindings.json` on the environment's machine: a JSON array of `{ "key", "command", "when" }` rules. - [all] Precedence: the last rule whose key and condition both match wins, even if it belongs to another command. Put specific rules after general ones.
- [all] `thread.stop` interrupts the focused thread's running turn (no default). `thread.undo` (`mod+z`) reverses the actions in the sidebar-bottom notice (unpin, settle, snooze, archive, discard draft); the notice stays for five seconds; terminals keep their native undo.
- [web] [desktop] `navigation.back` (`mod+[`) and `navigation.forward` (`mod+]`) move through visited pages. `chat.new` may ask for a project; `chat.newLocal` skips the chooser; `chat.newWithoutProject` (`mod+alt+n`) starts a thread without a project.
- [desktop] Reserved: `mod+w` closes the focused terminal or active right-panel tab, then the window; in a browser it closes the browser tab (rebind `rightPanel.close` and `terminal.close`, for example to `alt+w`). `mod+shift+t` reopens the last closed tab (files, diffs, pull requests, browsers, devices) and does not undo deleted work.
- [desktop] Quit: `Cmd+Q` (macOS) or `Ctrl+Q` (Windows/Linux). Default **Hold** mode: hold 1.2 seconds or press twice within 500 ms (needs keyboard repeat). **Settings → General → Confirmations → Quit shortcut** can be **Direct** (single press) or **Double press**. The application menu's **Quit** always quits immediately.

## portable-handoffs.md

- [all] T3 Code transfers conversation context when you switch providers, continue through a portable restart, or use a fork the provider cannot resume itself.
- [all] Short conversations transfer intact. Longer ones favour recent requests and answers, the original request and relevant activity such as command outcomes. Selected messages keep their full text, order and user or assistant role, including partial work from failed or interrupted turns. Your new request is never shortened to make history fit.
- [all] Codex receives historical messages directly when its installed version supports it; other providers receive the same selection as attributed context. Reasoning, tool-call state and attachments are not copied.
- [all] Omitted history is referenced; the agent can use T3 Code's thread-reading tool to retrieve it. A handoff is a budgeted selection, not an agent-written summary.
- [all] If even the references cannot fit, T3 Code reports an error rather than shortening the request. Compact the target conversation or pick a larger-context model.
- [cli] `T3CODE_CONTEXT_HANDOFF_TOKEN_CAP` sets the initial history allowance (default 16,000; clamped 1,024–64,000). Imported history has a separate 64,000-byte ceiling.
- [all] Capacity comes from model and option information plus provider telemetry. A fresh provider conversation clears prior usage; changing models or context-window options discards stale usage and compaction thresholds.
- [all] With no capacity information, T3 Code assumes a 128,000-token window and reserves at least 16,000 tokens (or a quarter of the window if larger). Images reserve an estimated 8,192 tokens each; other attachments 4,096 each.

Settings paths: none (server environment variable only).
Shortcuts: none.
States and messages: none quoted; the error when a handoff cannot fit is described but not quoted.

- [web] [desktop] **Deliveries** in a task's menu shows recent requests and the prompt each produced.
- [all] If the environment is offline the sender gets an error and nothing runs. **Hold webhooks while offline** in **Settings → Connections** makes T3 Connect keep requests for up to 24 hours and deliver them on return (request bodies are stored outside your machine). **Skip requests older than** on a task drops requests that waited too long.
- [all] Defaults and inheritance: **General** holds the model and workspace for new threads; **Integrations** controls agent browser access (changes apply when an agent session next starts); **Source Control** holds automatic pull, the default pull request merge method and text generation. ## remote-access.md

- [desktop] T3 Connect: on the host open **Settings → Connections**, sign in, and enable **T3 Connect** for that environment (no router forwarding needed). Command-line host: `t3 connect`. Changing network access restarts the desktop app. Command line: `t3 serve --host <private-ip>`; `t3 pair` makes a fresh link on a running server; scan the QR code or paste the URL into **Add environment**. `127.0.0.1` reaches only the device that opened it. Addresses in `100.64.0.0/10` shown as VPN unless the machine confirms Tailscale.
- [all] While connected through T3 Connect or a paired address, T3 Code learns the machine's current LAN and Tailscale addresses and adds them as routes (machines must allow network access for LAN learning; the background service allows private networks by default). Learned routes can be reordered but not removed.

- [web] [desktop] Select the route count under the machine's name in **Settings → Connections** to see routes; drag to reorder or remove. Mobile: **Settings → Environments** → **Edit**. Signing out of T3 Connect removes only that route.
- [web] [desktop] **Permissions** next to **Routes** (mobile: **Your permissions** in route details) shows what the current connection can do; it applies only to the route marked **In use**. Direct pairing and T3 Connect have separate sessions and may grant different permissions.

- [web] [desktop] Tailscale HTTPS: join both devices to the tailnet, enable **Tailscale HTTPS** in **Settings → Connections** (turn off to remove the route). Agents keep using tabs with no device connected; `localhost` reaches host servers. The first tab downloads headless Chrome (about 120 MB) into the T3 home, the same browser HTML renders use.

Take control before typing into an agent's tab and release it to let the agent continue; read-only connections can watch without changing the page. While you have control, copied text goes to your clipboard, page file pickers open your device's picker, finished downloads are offered for saving (downloads stay on the host until the tab closes), popups open as their own tabs, and audio does not play on your device.

It allows Chrome's sandbox with an AppArmor profile and installs libraries and system fonts with apt; it is safe to run again; without sudo it only reports. `T3CODE_SERVER_BROWSER_SANDBOX=0` runs without the sandbox where the host cannot be changed.

## t3-connect-troubleshooting.md

- [all] A T3 Connect connection has four parts in order: this device reaches T3 Connect; T3 Connect checks sign-in and the host's link; the host's tunnel (cloudflared on the host) carries the request; T3 Code on the host answers.
- [web] [desktop] When a connection fails, open **Settings > Connections**, find the environment and select **Details**. The first part marked failed is the cause; each cause has a section in the doc.
- [cli] Host side: `t3 connect status` on the host, or **Settings > Connections** on the host, checks the host's T3 Connect address from the host. `t3 connect` runs the same check when setup finishes. It cannot test another device's network; use **Details** on that device.
- [all] Tunnel offline: the host is asleep, off or offline, T3 Code is not running, or the host's network blocks the tunnel. Fix by waking the host, running T3 Code, running `t3 connect status`, and (after a long offline period, when T3 Connect removes the tunnel) starting and updating T3 Code to get a new tunnel.
- [all] Port 7844 blocked on the host: the tunnel connects out to Cloudflare on TCP and UDP 7844 (QUIC and HTTP/2). Common causes: a Tailscale exit node on the host (`tailscale set --exit-node=` to turn it off), a work VPN, or a strict firewall. Without T3 Connect, a direct route (the host's Tailscale address) works when both are on the same tailnet.
- [all] Tunnel up but T3 Code does not answer: T3 Code stopped, crashed or is starting; it restarted on another port after an update; or `T3CODE_HOST` binds only one address while the tunnel sends to `127.0.0.1`. Fix: restart T3 Code (`t3 service restart` for the background service), then run `t3 connect status`.
- [all] The T3 Connect address does not resolve, refuses the connection, fails TLS or times out: make sure the host is awake and online, run `t3 connect status`, and if only the host fails check its DNS, VPN or proxy.
- [all] This device cannot reach T3 Connect: check the device's internet (captive or dead Wi-Fi), turn off a VPN, firewall, ad blocker or DNS filter to test, and on iPhone turn off **Connectivity Assist** in Wi-Fi settings. Try another network or a direct route such as the host's Tailscale address.
- [all] Sign-in, account or link problems: the host is linked to a different account (sign in to the same T3 Connect account on both; on the host run `t3 connect logout` then `t3 connect`); **T3 Connect** is off on the host (turn it on in **Settings > Connections** or run `t3 connect`); the link was not applied yet (`t3 service restart` or restart `t3 serve`); this device's sign-in expired (sign out of T3 Connect and back in); or the account reached its tunnel limit (remove an unused environment from the T3 Connect page and restart T3 Code on the host).
- [all] Clock: T3 Connect rejects requests signed with short-lived proofs when either device's clock is minutes off; turn on automatic date and time on both, then retry.
- [all] Host running an older T3 Code: update it (see updating.md).
- [all] T3 Connect errors: `environment_link_limit_exceeded` or managed tunnel limit (remove an unused environment, restart T3 Code on the host); `auth_invalid` or `invalid_bearer` (`t3 connect login`; if revoked, `t3 connect logout` then `t3 connect`; restart the server after signing in); expired or invalid link proof (check the host's clock, update, restart); HTTP 403 without a recognised error (check relay access, proxies, firewall; keep the Cloudflare Ray ID); HTTP 408, 429 or 5xx (wait; T3 Code retries temporary failures itself). After a permanent fix, `t3 service restart`, or stop and rerun `t3 serve`.
- [cli] If T3 Code on the host disappears when SSH closes, see background-service troubleshooting (linger).
- [all] Reporting a problem: open a GitHub issue including the text from **Copy diagnostics** in the environment's **Details**, the output of `t3 connect status` on the host, and any trace ID shown.

Settings paths: **Settings > Connections** (written with `>`; web/desktop, on the device and on the host).
Shortcuts: none.
States and messages: **Details**; **Copy diagnostics**; **T3 Connect**; **Connectivity Assist** (iOS Wi-Fi setting); "This device"; "The host's tunnel is offline" (section heading); error codes `environment_link_limit_exceeded`, `auth_invalid`, `invalid_bearer`; "HTTP 403 without a recognized error"; "HTTP 408, 429, or 5xx".

## telemetry.md

- [all] The T3 Code server sends product usage events to T3 Code's endpoint `ingest.t3.codes`, tagged with a hashed account or installation identifier.
- [all] To count installations per person, the server also sends hashed account identifiers: the T3 Connect account, OpenAI and Claude accounts when signed in, and a random ID per connecting device. The endpoint keeps a copy of each event and forwards events to PostHog.
- [all] Event fields: provider, model, reasoning effort, permission mode, turn result, duration, release channel and main-agent token totals when available.
- [all] Not included: prompts, responses, file contents, authentication tokens, conversation IDs, raw provider events or child-agent output. Child-agent token use is excluded from totals.
- [all] Relay connection traces are sent to Axiom to diagnose T3 Connect connectivity.
- [cli] Opt-out is by server environment variable only: `T3CODE_TELEMETRY_ENABLED=false` before starting the server disables product events and relay tracing. Relay tracing also stops when `T3CODE_OTEL_SDK_DISABLED` or `OTEL_SDK_DISABLED` turns OpenTelemetry export off.
- [web] The web app in a browser, including one opened by the `t3` CLI, does not read these variables.
- [desktop] The desktop app reads `T3CODE_TELEMETRY_ENABLED` from the shell profile (for example `~/.zshrc`) on macOS and Linux; export it there and restart the app. On Windows set it as a user environment variable.
- [web] [desktop] Export diagnostics to your own receiver: **Settings > General > Diagnostics** → select an environment → enter each signal's OTLP HTTP endpoint under **OpenTelemetry export** (for example `http://localhost:4318/v1/traces`) → Save → restart that environment's server. The receiver must be reachable from the server's machine.
- [web] [desktop] **Test** sends an empty export from the server to check an endpoint; saved endpoints are checked when the section opens. Auth headers go only to the signal's running endpoint; redirects are not followed. For an authenticated new endpoint, save and restart first.
- [web] [desktop] `T3CODE_OTLP_*_URL` and standard `OTEL_EXPORTER_OTLP_*` variables override saved settings; an overridden signal shows **Set by environment** naming the variable, and its **Test** checks the running endpoint.
- [cli] `T3CODE_OTLP_HEADERS` supplies auth headers and `T3CODE_OTLP_PROTOCOL=http/protobuf` suits receivers that do not accept JSON (for saved or `T3CODE_OTLP_*_URL` endpoints). Endpoints set with `OTEL_EXPORTER_OTLP_*` use `OTEL_EXPORTER_OTLP_HEADERS` and `OTEL_EXPORTER_OTLP_PROTOCOL`.

Settings paths: **Settings > General > Diagnostics** (written with `>`); **Settings > General > Diagnostics** → **OpenTelemetry export**.
Shortcuts: none.
States and messages: **OpenTelemetry export**; **Test**; **Set by environment**; **Save**.
Note: the doc describes no in-app toggle for product usage telemetry; opt-out is environment-variable only.

## terminal.md

- [all] Each terminal keeps up to 5,000 lines and 8 MiB of scrollback on its environment server. The oldest output is removed when either limit is reached; a long line may be shortened at its start; new output is not truncated.
- [all] These limits apply on reconnect and when saved terminal history is restored; a client can show less scrollback than the server keeps.

Enabling queries can restore the startup wait.

## thread-migration.md

- [all] On the first V2 launch T3 Code copies the V1 `state.sqlite` into `statev2.sqlite` in the same data directory and migrates the copy. Threads appear automatically with full transcripts imported as needed; no import command is needed.
- [all] V1 keeps using its original database while V2 uses the copy; the import can run while V1 is open. The copy happens once: later conversations and changes do not sync between versions. Settings, attachments and workspace files stay shared.
- [desktop] The V2 desktop app uses a separate browser profile, so cookies and caches do not carry over; websites opened in the app may need sign-in again. On first launch V2 copies stashed prompts, unsent drafts, layout and theme from V1; later changes stay in V2.
- [all] A migrated thread keeps its title, project, provider and model selection, permission and interaction modes, branch or worktree, archive, settlement, snooze and pin state, and linked pull request, plus user and assistant messages, timestamps and supported attachments. Large histories can appear in stages.
- [all] Not converted: the old provider's live session, old run records, checkpoints and diffs, tool activity, approval history and proposed-plan history. These can be absent from a migrated timeline even though the conversation text is present.
- [all] The first new message starts a fresh provider session. T3 Code selects intact user and assistant messages using the same handoff budget as a provider switch (see portable-handoffs.md); omitted text stays in the thread and can be retrieved by the agent. The migration keeps a separate 32,000-character recovery excerpt; neither it nor the handoff replaces the full transcript.
- [all] Before continuing a long or important thread, restate older requirements in your next message; a new thread with a short handoff can be better when the old conversation has conflicting instructions.
- [cli] No whole-thread export command exists. Before a major server update, stop the server and copy its `userdata` directory (default `~/.t3/userdata`; with `--home-dir <path>`, `<path>/userdata`).
- [cli] Inspect a copied legacy database read-only with `sqlite3 -readonly`, listing `projection_threads` (`thread_id`, `title`, `updated_at`) and printing `projection_thread_messages` for one thread. Do not edit the recovery copy or point a server at it; for remote environments, do this on the machine running them.

Settings paths: none.
Shortcuts: none.
States and messages: `statev2.sqlite`; `state.sqlite`; "V1" and "V2" (version names used in the doc); `sqlite3 -readonly`; `projection_threads`; `projection_thread_messages`.

- [web] [desktop] Command palette `Cmd/Ctrl+K` searches threads across connected environments by title, branch, pull request or project; frequently and recently opened threads rank higher. **In messages** lists threads whose messages contain all your words and opens at the match (words need three or more letters, two for Chinese, Japanese and Korean). - [all] **Limited** means the provider stopped on a usage or rate limit; the conversation keeps the provider's explanation. - [all] **Snooze until reset** hides the thread until its allowance returns. ## updating.md

- [all] The app and the server running agents can be on different machines. When a server is behind the web or desktop app, an update notice appears in the conversation and in **Settings → Connections**; update the machine the notice names.
- [web] [desktop] The update button at the bottom of the sidebar updates every connected machine in one step, in order: outdated providers, then servers behind, then the desktop app. Servers move to the version the desktop app is installing (or the web app's version). A background service stays on its release channel; a remote desktop app installs the latest release from its own channel. Hover the button to preview; it widens to show progress, names slow machines, and offers **Retry** for a failed server; click to see every machine.
- [desktop] The desktop app restarts after each server has begun its own restart, following a short countdown. **Later** keeps working; restart from the update button when ready. A server still restarting finishes on its own.
- [all] Server updates appear only after the version is published to npm; remote desktop apps do not wait for npm. The confirmation lists each machine it skips and why (for example offline or manual update needed).
- [desktop] If a desktop app restarts on its old version, T3 Code says the update did not apply; it does not reinstall on its own, even when another device asks. Use the update button on that machine to retry.
- [all] The confirmation counts running threads the restarts will interrupt and how many can resume afterwards (see **Continue threads after restarts**).
- [all] **Settings → General → Continue threads after restarts** is on by default: supported active threads resume after an update, crash or machine restart. It is saved to connected environments that support it (update older servers first; use **Apply to all** after an offline environment connects). It does not enable automatic startup. Terminal commands can still be interrupted; threads without saved provider resume state need a new message. A thread that waited on a subagent, a background task, or a command or monitor the agent said it was waiting on is woken and told that work stopped. Other background shells (such as a dev server) do not wake it. Threads waiting for approval, an answer or a secret, or archived, snoozed or settled, are not resumed. After three automatic resumes in a row the thread waits for your message.
- [all] Updates from the previous orchestration system keep conversation transcripts but cannot carry all runtime history; read thread-migration.md before continuing an important older thread.
- [all] Version mismatch: a client and server must speak the same orchestration protocol. An app newer than the server is blocked before connecting with a notice to update the machine named; a server newer than the app refuses with an update message. Update the side the notice names, then reconnect.
- [all] Connected server actions depend on how it runs: **Update server** (keep the client open; supported background services update remotely; a desktop-hosted server also relaunches the desktop app on the host); **Update the desktop app** (on the server's machine); **Copy update command** (runs on the host to update a detected global npm install, then restart with your options); **Copy relaunch command** (stops the command-line server and relaunches with the copied command; does not update an installed `t3` command).
- [cli] On the host, `t3 update <client-version>` (the version shown in the notice). It asks before restarting the background service; if declined, run `t3 service restart`. A hand-started server must be stopped and started again with its usual options. If the server runs via `npx`, relaunch as `npx t3@<client-version>`.
- [all] If an update fails: keep the client open until it reconnects or reports failure (a failed service update can roll back). Retry the offered action once; check you updated the server's machine; relaunch the exact version for a command-line server. Only one server can use a T3 home at a time; stop the other or use a separate home directory and pair with the running server.
- [web] [desktop] Providers: **Settings → Providers** shows provider updates for the selected environment. **Update all** updates every outdated provider on every connected environment (hover to see the list; providers with manual-only update commands are excluded). After a successful provider CLI update, model discovery refreshes for each enabled instance using its own configuration. Provider updates do not restart running chats; an existing session keeps the old CLI until it ends.
- [mobile] Update an environment from **Settings → Environments** → select it → **Check for updates** (latest release on that environment's channel). Keep the app open while it updates and reconnects; hosts that cannot update remotely show instructions for the machine. The same page refreshes provider status and updates supported providers (needs a connected environment and permission to operate it).
- [mobile] **Settings → Maintenance** holds provider update checks and restart-continuation preferences. Provider update checks also gate downloading model catalog updates; with them off, new models may not appear until enabled and status is refreshed.
- [mobile] App Store and Google Play releases install as usual. The app can download updates in the background and apply them on your next exit, saving drafts and queued messages first. If left open a long time it may ask to install now; **Later** queues the update.

## usage.md

- [all] **Usage** combines Codex, Claude Code, Grok Build, OpenCode, Antigravity, Pi, Muse Code and Cursor history from connected environments: token use, cache savings, model breakdowns and estimated API-equivalent cost split by token type and speed. - [web] [desktop] Refresh Usage to rescan session history and update model pricing when recent work is missing or a new model shows no cost.
- [web] [desktop] **Model prices** (environment dropdown on Usage) adds, edits or resets an estimated price per model: **Apply to** (starts from the current filter), exact model ID, USD per million input and output tokens; optional cache read and write rates (blank uses the input rate; `0` for free). - [web] [desktop] **Map to** counts one model as another (for example a preview model under its released name): the mapped model leaves **Usage** and its tokens and cost move to the target's price. Clearing **Map to** or resetting the row restores it.
- [web] [desktop] Each destination reports whether a price change saved; offline or unavailable environments show **Not saved**. **Retry failed saves** finishes the same change for them without rewriting environments that already saved. Changes are not queued after the dialog closes.
- [web] [desktop] **Usage → Limits** pools subscription accounts per provider: one number per window, with a bar of one segment per account ordered by next 5-hour refill. Window cards show what is left and when the next reset lands (the hatched part is what the reset restores). Tap a segment or account row for plan, sign-in location and reset time. Narrow screens show numbered rows under the bar.

A Claude or Codex account with no weekly quota left shows 0% left for its pooled session contribution; refill estimates need valid reset times; Claude's model-specific weekly allowances keep reported values.
- [all] Opening Limits checks selected connected environments automatically; each client waits at least five minutes between automatic checks of an environment (including after a failed one). Refresh Limits to re-check every provider and hub.
- [all] `/usage-limits` (composer command menu or sent as a message) shows the current model's limits above the composer until dismissed or the next message. It uses the same snapshot as **Usage → Limits** and does not run the agent. Offered only for providers listed under **Usage → Limits**.

API-key accounts, and Claude proxied through `ANTHROPIC_AUTH_TOKEN`, may not report subscription limits.

Accounts appear under **Usage → Limits** (no hub plugin needed). This supplies usage data only; configure the provider separately to send requests through the hub. Remove the hub in the same section.

Setup can be left at any point except during an import.
- **What it checks.** Selected computers are connected before continuing; the workspace is confirmed at startup (**Still connecting**, with **Reload**); saved settings are readable (**Could not read settings**, with **Retry**; setup never replaces unreadable settings with defaults); the computer's T3 Code version is compatible (**Client not supported**, with a message naming the side to update); Claude Code and Codex are installed and signed in; project import scan limits (warned when projects or conversations may be missing).
- **Re-entering setup.** Open `/welcome` to run setup again. Settings lets you connect computers and agents later. Direct links such as Settings open before setup is done. The hosted app at app.t3.codes skips setup and, with no computer connected, asks you to sign in to T3 Connect and run `npx t3 connect` on your computer.
- **install.md (first run).** The install commands are `curl -fsSL https://t3.codes/install.sh | sh` (macOS and Linux) and `irm https://t3.codes/install.ps1 | iex` (Windows PowerShell); the desktop app comes from GitHub Releases or a package manager. Requirement before the first thread: an installed, authenticated provider. Provider setup is under **Settings → Providers** on the environment's machine. Mobile: App Store or Google Play, then link to a server through remote access or a pairing URL. **Settings → Diagnostics** shows startup crash reports on the next successful launch.
- **remote-access.md (first connection).** Desktop host: **Settings → Connections** → sign in → **T3 Connect** for that environment (command line: `t3 connect`, approved with a browser link and short code over SSH). Other devices sign in to the same T3 Connect account and choose the environment; the app.t3.codes home page adds compatible computers. Direct pairing: **Settings → Connections** → **Network access** → pairing link, or `t3 serve --host <private-ip>` and `t3 pair` (QR code or pasted URL into **Add environment**). Mobile connection settings are under **Settings → Environments**. Desktop SSH: **Settings → Connections → Add environment** → **SSH**.
- **outside-agents.md (first sign-in for an outside agent).** The agent's sign-in page on the environment names the agent; approve with a pairing code from **Settings → Connections** or `t3 auth pairing create`; choose the access level (**Read only** by default).

## Platform differences

- **Settings entry point.** Web and desktop show full Settings pages with a "Applying settings for …" line that picks the project and environment. Mobile shows a single **Settings** list with a filter in its header that chooses environments and a project; device-only settings (Appearance, keyboard) ignore the filter.
- **Environment and server settings.** Web and desktop change one environment at a time (or **All environments**). Providers and diagnostics are per machine on every client. Mobile edits connected environments' defaults through **Server settings** and **Thread behavior**.
- **Appearance and themes.** Custom themes can be created, imported and exported only on web and desktop. Mobile has its own themes and text, code and terminal preferences, and does not follow environment themes or defaults. Android 12+ can use **Material You** colours and **Material You Layout**. app.t3.codes does not use environment themes.
- **Keyboard and shortcuts.** Keybinding customisation and most shortcuts are web and desktop. An iPad with a hardware keyboard gets `Cmd+1` to `Cmd+9`, `Cmd+K` and `Cmd+Shift+H`. Hardware keyboards on mobile use `Cmd` to switch the send action. `mod+1` to `mod+9` thread jumps are desktop-scoped by default (`isDesktop`) so browsers keep their tab shortcuts.
- **Composer.** Enter sends on all clients. Follow-up choice is **Settings → General → Follow-up behavior** on web and desktop and **Settings → Follow-ups** on mobile. Mobile offers long-press for the other action; web and desktop use the send button with the modifier. Citations (**Cite in composer**) and "Edit from here" are web and desktop only; mobile can display saved quotes. Context chips are created on web and desktop (`#`, `@`, drag); on mobile a chip is tapped to inspect. Mobile adds iPhone voice input (iOS 26+), share-sheet intake and HEIC conversion from the photo library.
- **Offline behaviour.** Mobile keeps local drafts and queued messages while disconnected, and they survive restarts; web and desktop do not document this.
- **Activity log.** Expandable tool-call summaries are described for web and desktop only.
- **Threads and sidebar.** Pinning and dragging between sections is web and desktop; mobile reorders through **Arrange threads** and **Move up** and **Move down**. The **Working section** beta is switched in **Settings → Beta → Working section** on web and desktop and in **Settings → Thread behavior → Working section** on iOS and Android. Thread search includes message matches on mobile. Auto-balance across machines is web and desktop only; mobile keeps the manual environment choice.
- **Notifications.** Device Notifications, Ongoing Agent Activity and Live Activity Updates exist only on mobile. Notification permission and Android channels are in the OS settings.
- **Usage.** Usage page with the environment dropdown, Model prices, Map to and Retry failed saves are web and desktop. Mobile has the Subscription usage widget (iOS and Android) and **Usage** in workspace navigation.
- **Devices.** The Device panel is in the right panel on web and desktop, with a floating window option; agents' devices float over the chat there. On mobile the device button above the composer opens the live screen. Remote live video needs HTTPS or localhost; on plain HTTP iOS falls back to still images and Android cannot show video.
- **Browser.** The desktop app shows its own environment's browser tabs directly; web and mobile stream them from the host. "Pop into separate window" (picture-in-picture) is mobile only. Browser import from other browsers (**Settings → Integrations → Browser profiles**) is desktop only; Safari import on macOS needs Full Disk Access.
- **Desktop-only features.** Default web browser (macOS only, System Settings). SnapShots (macOS, Windows, Linux Wayland; X11 unsupported). The `t3` command install (**Settings → General → About**). Remote-only desktop mode (**Local environment** switch). The quit shortcut confirmation. `mod+w` and `mod+shift+t` reserved shortcuts.
- **Background service.** Linux and macOS only; Windows background services are not supported. macOS starts the service at login and stops it at logout.
- **Storage reclaim suggestion.** **Settings > Storage** on web and desktop; **Settings > Maintenance** on mobile.
- **Pull requests.** Mobile lists reviews across environments and offers **Work on PR**; line comments stay as drafts until submitted. Shift-click quick actions and bulk close (**Close**) are web and desktop. Review guides are on all three clients; on mobile they are read with **Next** between stops, while commenting on a stop and **Ask about this stop** / **Finish review** are web only.
- **Telemetry configuration.** The web app in a browser does not read `T3CODE_TELEMETRY_ENABLED`; the desktop app reads it from the shell profile on macOS and Linux and from a user environment variable on Windows.
- **Permissions view.** **Permissions** next to **Routes** on web and desktop; **Your permissions** in mobile route details.
- **Updates.** The sidebar update button (web and desktop) updates all machines; mobile updates one environment at a time from **Settings → Environments** → **Check for updates**; the mobile app applies its own updates when you next leave the app.
